# Duo Wallet UI/UX audit

Audit date: 4 November 2026. Reviewed the current working tree, including the user's uncommitted redesign. No application source changes were made for this audit. Line references describe this snapshot and will move during implementation.

## Verdict

**The app is a promising prototype, but it does not yet meet the usability, accessibility, or trust bar of a mature consumer finance app.** This is not primarily a matter of adding decoration. The most serious problems are invented chart history, controls that imply working protection or cloud connectivity, incomplete privacy masking, inaccessible custom controls, and layout failures on ordinary narrow phones. Those need to be resolved before visual polish can earn users' trust.

The good foundation should be preserved: shared versus personal concepts are explicit, several screens already explain debt calculations, most long pages scroll, major amounts use tabular figures, and many headings and names have sensible truncation. The coral/teal palette is recognizable. The recent account details screen makes accounts feel much more tangible. The work needed is to make these patterns coherent, truthful, legible, and complete.

Airbnb and Instagram are useful quality references for clear hierarchy, familiar navigation, predictable interactions, and attention to small details. They are not a reason to copy their colors or feature set. A finance app also has a higher burden to explain what a number means and whether an action actually moved money.

## What was inspected and how certain the findings are

Read `theme.dart`, `router.dart`, `app.dart`, `main.dart`, all 17 presentation files, the existing widget test, and relevant database, money, domain, and test code. Root verification reported `flutter analyze` clean and all 18 pre-existing tests passing. Those checks do not demonstrate UI readiness: the existing widget test exercises a few navigation and language changes at the default test viewport.

The audit additionally rendered the real Flutter widget tree with seeded data, actual Roboto and Material Icons fonts, and normal shadows. It visited 16 routes at four configurations: EN 360×800/1× text, HU 320×640/1× text, HU 320×640/1.5× text, and EN 360×800/2× text. Pages with a main `ListView` were scrolled five times. Transaction and transfer sheets were also opened at both normal text configurations. A separate dark dashboard capture was inspected.

**64 route/configuration visits produced 33 captured rendering-error events.** These events are repeated instances of a smaller set of layout defects, not 33 separate product bugs. One small dashboard chart overflow was logged during a configuration rebuild and is described separately below. A zero in the matrix means no Flutter rendering exception was collected for the seeded content at that configuration; it is not a guarantee that every state fits.

The temporary collecting harness deliberately records Flutter errors instead of failing immediately so it can finish the matrix. Its completion status must not be interpreted as passing accessibility or layout tests. Screenshots and diagnostics are in [UI evidence](ui-ux/before/). The temporary reproducible harness remains in `app/test/ux_review_probe_test.dart` for conversion into portable regression checks. The harness uses the Flutter SDK font directory from this machine; adapt that path before rerunning elsewhere.

Evidence labels throughout this report:

- **Observed:** visible in the actual rendered widget tree or captured in Flutter's layout diagnostics.
- **Source-confirmed:** directly established by code, without claiming a manual end-to-end reproduction.
- **Risk:** a plausible failure requiring the specified follow-up scenario.
- **Design judgment:** a usability or visual quality judgment supported by the inspected layout.

Not exercised: a physical Android phone, real software keyboard, TalkBack, actual biometric authentication, real cloud accounts/sync, Android share/file pickers, background execution, a large production database, every modal/dialog, or long-name/extreme-value fixtures. These are release checks, not presumed passing behavior. Initial Ahem-font screenshots were discarded. The apparent black outline around the initial FAB captures was a Flutter test shadow artifact and is **not** a reported app defect.

## Prioritized findings and exact remediation

Severity: **P0** = blocks a trustworthy production claim; **P1** = core task/accessibility or substantial layout failure; **P2** = material friction or inconsistent polish; **P3** = smaller clarity improvement. Implementation should close findings by ID, with evidence; a redesigned screenshot alone does not close behavioral issues.

### Trust, financial meaning, and privacy

**UX-01 · P0 · Authentication and household connectivity are simulated.** Source-confirmed: `auth_screen.dart:20–29` prepopulates a demo email/password and initializes `_signedIn = true`; `523–535` changes a boolean and announces registration/sign-in without authenticating. `151–168` can report household connection or simply update the local household. The default provider seeds Sam/Anna (`app_database.dart:616–624`), while the profile screen exposes a privacy-test identity switch (`auth_screen.dart:192–240`). A normal user can reasonably believe their data is associated with a protected, connected account. **Fix:** show one explicit, persistent demo/local-only explanation; gate the identity simulator as a clearly named demo tool; hide or disable real-auth/join controls until wired to actual results. Keep editing a local profile separate from signing in. **Accept:** an invalid email/password never produces a signed-in or registered state; no unverified cloud connection claim; a fresh launch makes the current data mode understandable.

**UX-02 · P0 · Security and update settings overpromise.** Source-confirmed: app lock only writes `appLockEnabledProvider` (`settings_screen.dart:13,113–123`); the app/root does not enforce it. Update status is derived from `Env.isConfigured`, not a release check (`262–272`). The setting falsely implies biometric/PIN protection, and a configuration flag falsely implies the installed app is current and signed. **Fix:** disable unavailable lock/update actions with a concise explanation or wire their actual capabilities; never show success based on a local toggle/config flag. **Accept:** enabling lock either invokes/installs real protection or clearly says unavailable; an update claim requires fetched version evidence. Backend/native implementation is a separate readiness project if outside this UI work.

**UX-03 · P0 · Charts invent financial history.** Source-confirmed and observed: `dashboard_screen.dart:84–99` replaces missing historical months with fractions of this month's spend, then uses that manufactured baseline to calculate a percentage change. `stats_screen.dart:127–133` similarly inserts made-up expenses and income. The seeded dashboard’s `+18.3%` comparison itself reconciles to the recorded current and preceding month; it is not evidence of fabrication. The older chart bars are manufactured, and the fallback comparison would also be manufactured when the preceding month is empty. **Fix:** remove display-time synthetic data; leave missing months empty/zero as appropriate, distinguish no data from zero if the product has that information, and show “No previous month to compare” instead of a false delta. Seed fixtures may contain explicitly demo transactions; the renderer must not invent them. **Accept:** a database with one current-month transaction shows no historical spending/income unless actual rows exist; deltas reconcile exactly with underlying periods.

**UX-04 · P1 · Hiding amounts still exposes amounts in activity prose.** Source-confirmed: `activity_screen.dart:87–105` masks the trailing amount but displays `act.localizedSummary(...)` unchanged. Activity summaries embed numeric amounts (`transactions_screen.dart:550–559`, `transfer_sheet.dart:166–175`, `goals_screen.dart:90–95`, `settle_up_screen.dart:213–216`). Dashboard activity does the same (`dashboard_screen.dart:822–830`). **Fix:** render amount-free structured summaries while masking, or mask a safely structured amount token; do not apply fragile arbitrary-number replacement to merchant names. Specify that explicitly opening an editor may reveal its amount. **Accept:** enabling Hide amounts removes transaction, contribution, and settlement figures from both activity surfaces and accessible labels; chart scale/tooltip behavior follows the same documented privacy policy.

**UX-05 · P1 · Report currency control changes a preference without changing reports.** Source-confirmed: `settings_screen.dart:68–82` updates `displayCurrencyProvider`; main summaries, stats, history and goals construct HUF amounts directly, and the preference is not consumed by those reports. **Fix:** either implement coherent conversion with displayed currency/rate context for every report, or remove/disable this preference and clearly state that reports use HUF. Prefer the honest smaller fix for this UI scope. **Accept:** choosing EUR cannot leave an apparently successful setting alongside unchanged, unlabeled HUF reports.

**UX-06 · P1 · Amount component damages locale-specific decimal notation.** Source-confirmed: `theme.dart:862–868` runs `NumberFormat` then replaces every comma with a space. A Hungarian EUR/RON value such as `12,34` becomes `12 34`, corrupting the decimal separator. Other screens use `Money.format`, so the same money can have two notations. **Fix:** use one locale-aware money formatting path; split numeric and currency styling without postprocessing decimal punctuation. **Accept:** HUF/EUR/RON, positive/negative/zero, EN/HU, and fractional values display consistently; Hungarian EUR `12,34` retains its comma and English EUR `12.34` its period.

**UX-07 · P1 · Time scope and currency meaning are inconsistent across financial summaries.** Source-confirmed: stats totals aggregate all transactions (`stats_screen.dart:45–84`) under “Monthly Cash-Flow Trend” (`202–205`), while its line chart uses six months. Transactions totals are all-time (`transactions_screen.dart:76–79`) but have no period label. Dashboard month filter has no upper boundary (`40–42`) and includes future transactions; accounts' monthly flow does the same (`accounts_screen.dart:390–398`). Accounts opening/closing aggregates add native account units and display HUF (`402–409,667`); goal summaries also sum native goal units as HUF (`goals_screen.dart:302–308,412,438`). **Fix:** label and align periods; use `[monthStart,nextMonthStart)` for current month; convert before cross-currency aggregation or group totals by currency; make the cash-flow opening balance the month's opening, not lifetime account openings. **Accept:** known dated and multicurrency fixtures reconcile from list to chart to summary; future entries do not inflate this month's total; every summary states its period/currency.

**UX-08 · P1 · Private account route has no screen-level visibility guard.** Source-confirmed: `account_details_screen.dart:33–65` accepts any found account ID and builds its name, transactions and controls without ownership validation; the router exposes `/accounts/:id` (`router.dart:57–62`). Lists hide other users' accounts, but a route or retained page is another entry point. **Fix:** reject inaccessible/archived/deleted accounts before resolving their data; use a neutral unavailable screen and safe back navigation. **Accept:** navigating directly to a partner-owned account ID, including after the demo identity changes, reveals no name, balance, history or edit action. This does not substitute for backend authorization.

### Navigation, accessibility, and the shared design system

**UX-09 · P1 · Primary navigation relies on unfamiliar icons.** Observed and source-confirmed: the custom bottom row renders icons only (`router.dart:229–278`); tooltip and semantics labels do not help sighted first-time users identify dashboard, transactions, accounts, stats and settle-up. Finance concepts are less universally recognized than familiar social-feed icons. **Fix:** show short localized labels for all destinations, retain a clear selected indicator, and size the bar to content/system insets. **Accept:** a new user can identify all five tabs without a long press; EN/HU large text fits; selected state is visible and spoken.

**UX-10 · P1 · The feature menu is reachable only from Dashboard.** Source-confirmed: only dashboard explicitly opens `AppShell.openDrawer` (`dashboard_screen.dart:164–168`). Other screens use inner `Scaffold`/`AppBar` widgets without a drawer/menu control; the outer drawer is not their nearest scaffold (`router.dart:189–225`). **Fix:** supply a consistent menu affordance on top-level screens, or add an explicit More destination; use back affordances on subordinate pages. **Accept:** budgets/goals/settings/export can be reached from each primary tab without first returning Home; a subordinate page has an obvious exit.

**UX-11 · P2 · Tab navigation can discard context and mixes navigation models.** Source-confirmed/risk: bottom tabs call `context.go`, drawer entries generally call `context.push`, and routes use `ShellRoute` without per-tab preserved branches (`router.dart:29–122,253,284–297`). Filter/search and scroll state can be recreated when users move between tabs. **Fix:** choose one predictable navigation contract, preserve each primary tab's location/filters/scroll with a stateful shell or equivalent lightweight state, and keep explicit detail routes. **Accept:** switching tabs and back restores the previous filter and scroll; Android Back consistently dismisses a modal, returns from a detail, then exits at Home; repeated menu selections do not stack duplicate top-level pages.

**UX-12 · P1 · Custom pressables lack native focus and activation behavior.** Source-confirmed: `Pressable` builds a pointer `Listener` plus optional `GestureDetector` (`theme.dart:559–612`). It does not provide keyboard shortcuts, focus styling, a button role, or disabled state. Bottom tabs add semantics but no keyboard/focus behavior; clickable `DuoCard`, section actions, and avatar rely on the same primitive (`745–746,982–1007`; dashboard `209–222`). **Fix:** build controls on Material/native interactive widgets (`IconButton`, `InkWell`, `FocusableActionDetector` as appropriate), keep pressed feedback, avoid nested duplicate handlers, and add semantic names/roles/state. **Accept:** Tab/Enter/Space and TalkBack activate every visible action; focus is visible; disabled controls do not animate as enabled; one gesture invokes one action.

**UX-13 · P1 · Several targets are too small.** Source-confirmed: circle buttons default to 38×38 (`theme.dart:909–944`), dashboard chevron uses 20px icon plus 4px padding (`dashboard_screen.dart:563–571`), section links get only 4px vertical padding (`theme.dart:984–985`), and category chips explicitly shrink tap targets with negative density (`transactions_screen.dart:826–829`). **Fix:** retain compact visual glyphs inside at least 48×48 interactive bounds, with sensible spacing; restore comfortable chip tap areas. **Accept:** Flutter Android tap-target guidelines pass for these controls and adjacent controls are usable one-handed.

**UX-14 · P1 · Brand and status colors fail small-text contrast.** Source-confirmed/calculated: white on `#FF385C` is **3.52:1**; white on `#00A699` is **3.04:1**. These are used for 11–14px labels on buttons/badges (`theme.dart:218–228,343–351,636–643,662`). `#767676` on `#F7F7F7` is **4.24:1**, below 4.5:1 for small text; it appears in captions on the canvas. **Fix:** preserve brand hues for larger decorative surfaces but introduce darker accessible foreground/background variants for small text and controls. Check actual composited hero caption colors, chart labels and category colors too. **Accept:** text combinations meet 4.5:1 for ordinary text or 3:1 for sufficiently large text; nontext essential indicators are distinguishable without color alone. Calculations use sRGB relative luminance, not screenshot sampling.

**UX-15 · P2 · Semantic color and hierarchy compete with the brand.** Observed/design judgment: `DuoPill(solid:true)` makes an increase in spending teal/positive (`dashboard_screen.dart:249–252`), debt gets the same saturated coral used for primary actions, and dark neutral icons default coral (`theme.dart:195`). Goals use orange for incomplete progress without an actual warning (`goals_screen.dart:570–572`); the gauge transitions teal to coral for more completion (`theme.dart:1047–1048`). **Fix:** reserve coral primarily for actionable emphasis; keep neutral icons neutral; label comparison direction and period; use neutral comparison styling when more spend is not automatically good/bad; keep progress completion semantics consistent. **Accept:** users can distinguish action, danger, pending and success in light/dark/grayscale; an increase in spending is not presented as an unexplained success badge.

**UX-16 · P2 · Two card systems and many local styles weaken cohesion.** Observed/source-confirmed: `Card` uses radius20/border/no shadow (`theme.dart:301–309`), `DuoCard` radius24/no standard border/multiple shadows (`711–737`); screens mix both, 16/18/20/22 padding, stadium and rounded rectangular action shapes, dense list rows and bespoke wells. **Fix:** define a small set of shared surface types with a reason for each: summary card, grouped list, inset well, primary action. Normalize spacing, radii and section treatment while preserving the requested palette. **Accept:** account, budget, goal and settings cards share the same visual grammar; elevation/filled color expresses hierarchy rather than which widget a developer happened to use.

**UX-17 · P1 · Responsive layout fails even on normal small phones.** Observed: the overflow matrix above and the profile/transaction captures show both actual overflow and unreadable letter-by-letter segment wrapping. **Fix:** replace content-competitive Rows with `Wrap` or narrow-width Columns; move secondary actions below headings; stack summary values above toggles; make dropdowns expanded with bounded selected content; constrain large trailing amounts and give them a separate line at large text. Use available constraints plus text scaling, not a single hardcoded device width. **Accept:** zero captured Flutter errors at all four audited configurations and at 320×568; no midword vertical labels; all money values/actions remain readable. Do not close this by globally reducing text scale, shrinking every amount, clipping, or adding ellipsis to critical actions.

**UX-18 · P2 · Typography sometimes trades readability for fit.** Observed/source-confirmed: 10–11px mini-chart labels (`dashboard_screen.dart:899,924`, `stats_screen.dart:660,685`), 11px badge defaults (`theme.dart:527,662`), and unlimited `FittedBox.scaleDown` on money can make meaningful figures very small. A headline/gauge can remain large while useful supporting information becomes tiny. **Fix:** keep routine body/financial labels readable, give long amounts a responsive second line or an explicit compact representation with an exact detail, and avoid over-compressing typography. **Accept:** large amounts and 200% text retain legibility; category/status meaning remains readable without zooming; compact values have an exact-value route or accessible equivalent.

**UX-19 · P2 · Reduced motion support is partial.** Source-confirmed: Pressable and DuoAmount honor `disableAnimations` (`theme.dart:585,896`), but `_FadePageTransitionsBuilder` does not (`550–552`); bottom selection uses unconditional animation (`router.dart:255–257`), and dashboard chart height animates unconditionally (`dashboard_screen.dart:907–910`). All platform routes also replace native transitions with fades, including iOS detail navigation. **Fix:** gate custom motion on accessibility settings and distinguish frequent tab switches from detail navigation; retain native back/gesture expectations where relevant. **Accept:** reduced-motion mode avoids chart-height and route movement; rapid interaction is interruptible; no perceived delay on repeated navigation. Real-device gesture behavior remains a follow-up check.

### Entry, editing, and money movement

**UX-20 · P1 · Invalid forms often do nothing or silently coerce values.** Source-confirmed: account empty name silently returns and invalid opening balance becomes zero (`accounts_screen.dart:182–186`); budgets silently reject nonpositive values (`budgets_screen.dart:152–153`); goals do likewise (`goals_screen.dart:197–204`); recurring and categories share the pattern (`recurring_screen.dart:248–252`, `categories_screen.dart:135–146`). Transaction/transfer invalid input uses a generic Snackbar detached from its field, and rates permit fallback values (`transactions_screen.dart:452–477`, `transfer_sheet.dart:93–121`). **Fix:** use field-level validation with a plain corrective message; preserve user input; validate finite numeric values and valid positive exchange rates; show which account/category needs attention. **Accept:** empty, whitespace, zero, negative, malformed, decimal-comma, huge and nonfinite inputs produce understandable errors and never change a balance unexpectedly; focus moves to the first invalid field.

**UX-21 · P1 · Dates cannot be chosen in core entry flows.** Source-confirmed: transaction `_occurredOn` is initialized/restored but has no date control (`transactions_screen.dart:400,420,608–874`); transfer fixes it to now (`transfer_sheet.dart:56,142`); recurring rules set next due to today without a due-date field (`recurring_screen.dart:274`); goals ask for months instead of an actual date (`goals_screen.dart:176–182,218`). **Fix:** add a clear Today/date control to transaction and transfer, a first-due date to recurring setup, and a date picker/deadline display to goals. **Accept:** a user can record yesterday's expense, a scheduled transfer, a bill due next month, and an exact goal deadline; list/chart periods reflect the chosen date.

**UX-22 · P2 · “Quick Add” is a dense general-purpose form.** Observed/design judgment: one sheet includes transaction kind, amount/currency, manual FX, account, scope/split slider, all category chips, merchant, note, tags and Save (`transactions_screen.dart:649–872`). Common-account selections still expose a split slider even though common spending creates no personal debt. Save is at the bottom and a short helper line truncates the account rule. **Fix:** make amount, account, category and date the primary path; collapse optional details; use a single transfer flow; show a compact split summary only when meaningful. Give scope/privacy a visible explanatory label and use wrapping helper/error text. **Accept:** a normal expense can be saved without scrolling through notes/tags; Hungarian labels remain readable; common-account spending clearly explains its treatment; keyboard-open Save is reachable.

**UX-23 · P1 · Dismissal can discard financial drafts without warning.** Source-confirmed/risk: sheets/dialogs use default barrier/drag/back dismissal and do not track dirty state (`transactions_screen.dart:370–377`, `transfer_sheet.dart:31–40`, all editor dialogs). **Fix:** track changes from initial values and ask to discard only when a meaningful unsaved change exists; keep blank forms easy to close. Avoid forcing confirmation on every normal dismissal. **Accept:** after entering amount/note/profile changes, Back, close, barrier tap and sheet swipe either preserve the draft or explicitly confirm discard; canceling the discard keeps all input.

**UX-24 · P1 · Transaction deletion has no recovery or explanation.** Source-confirmed: menu Delete immediately soft-deletes (`transactions_screen.dart:312–313`, `account_details_screen.dart:324–325`); editor delete immediately closes (`transactions_screen.dart:635–637`). A soft delete in storage is not a user-facing undo. **Fix:** offer an immediate Undo Snackbar with a meaningful description, or confirm a consequential delete with item/amount context when undo cannot be reliable. Provide consistent behavior from list and editor. **Accept:** accidental deletion can be reversed visibly; the restored item retains shares/currency/account/date; balances and settle-up reconcile after deletion and undo.

**UX-25 · P2 · Transaction rows favor metadata over fast scanning.** Observed/source-confirmed: full ISO dates, payer, account, optional unbounded notes/tags, two amount lines and a menu share every row (`transactions_screen.dart:213–343`). Row tap opens edit directly; there is no stable read-only receipt/detail presentation. History rows cannot open anything (`history_screen.dart:225–246`). **Fix:** use consistent date grouping/localized dates; emphasize merchant/category and exact amount; bound optional metadata; open a coherent detail/edit sheet from every transaction surface with a clear Edit action. **Accept:** long merchant/note/account names and large amounts remain understandable; equivalent entries look the same across Transactions, History and Account History; users can inspect a receipt without accidentally editing it.

**UX-26 · P1 · Two transfer editors have inconsistent rules.** Source-confirmed: quick-add supports transfers (`transactions_screen.dart:649–655,753–772`) but its submit validation requires only amount/source, not a distinct nonnull destination (`452–453`); it stores destination amount equal to source amount (`526–528`). The dedicated TransferSheet validates different accounts and has cross-currency calculation (`transfer_sheet.dart:94–124`). **Fix:** route transfer creation/editing through one validated flow; keep selected transaction context, account currencies, destination amount and date intact. When editing someone else's shared expense, do not silently substitute the current user's personal account or invert the split: existing split initialization uses payer ID (`transactions_screen.dart:421–424`) while save computes using current user (`480–487`). **Accept:** transfers cannot be saved to the same/missing account; an EUR→HUF edit preserves the correct receiving amount; opening and saving an unchanged partner-paid shared expense preserves payer and shares.

**UX-27 · P1 · Transfer and settlement actions need an explicit financial outcome.** Source-confirmed/design judgment: transfer shows source/destination/rate fields but no receiving-value review (`transfer_sheet.dart:249–346`); an initially cross-currency sheet leaves rate `1.0` until an account-change callback recalculates it (`50,74–87,197–220`). A contribution toggle can be enabled for routes that are not a personal-to-common payment (`316–333`). Settlement proposal/confirm flows discuss internal account adjustment but can imply that money was sent (`settle_up_screen.dart:129–147,254–285`). **Fix:** initialize quotes from selected accounts; validate positive rates; show “From X: −amount / To Y: +amount” before saving; derive contribution classification from actual accounts. Explicitly say that recording a transfer/settlement does not initiate a bank payment. Show confirmation amount, parties and optional local balance effect. **Accept:** before saving, a user can predict both account changes and visibility; cross-currency initial values are correct; no control classifies a personal-to-personal movement as a common contribution; settlement confirmation identifies the actual proposal.

### Screen-specific completeness and hierarchy

**UX-28 · P2 · Dashboard prioritizes auxiliary utilities above daily decisions.** Observed/design judgment: the three prominent tiles are Excel Export, Past Months, Growth & Stats (`dashboard_screen.dart:445–521`), while no recent transaction list appears and budget/goal lists grow without a limit (`578–629,646–695,712–773`). At 360px the first account amount is under the FAB. **Fix:** keep a concise spend overview and settlement summary, put relevant account/budget or recent transaction information next, demote export to the menu, cap preview lists with View all, and reserve unobscured space for primary content. **Accept:** first viewport gives the key amount and next action; FAB never covers the only presentation of a balance/action; many accounts/goals do not create an endless dashboard.

**UX-29 · P1 · Settlement strip breaks the most important sentence.** Observed: at 360px `Anna owes Sam 4` wraps before `000 Ft`; the no-debt explanation is ellipsized (`dashboard_screen.dart:386–419`) alongside a separate pill-sized Settle Up action. **Fix:** separate direction/name from a nonbreaking amount, stack content at narrow widths, and make the whole strip a well-labeled action with a trailing chevron or full-width action. Keep policy text in a readable detail/expanded location. **Accept:** long partner names and large amounts do not split numeric groups; the strip communicates who owes whom and exactly how much in EN/HU at 200% text.

**UX-30 · P1 · Dashboard budget preview reports the wrong scope/category context.** Source-confirmed: dashboard uses all shared or personal monthly spend for every corresponding budget (`dashboard_screen.dart:649–651`), ignoring `b.categoryId` and rollover. Labels show only Shared/All Mine (`660–662`), while Budgets correctly computes per-category spend (`budgets_screen.dart:282–309`). **Fix:** share the budget calculation and title logic; present category/name, period, spent, remaining/over-limit, and effective limit consistently. **Accept:** a food budget shows food spend on both screens and has the same rollover-adjusted limit/percentage; at large text the monetary summary stacks above secondary controls.

**UX-31 · P2 · Account creation and empty-account states need direction.** Source-confirmed/design judgment: account groups render as loops without a clear group-specific empty state (`accounts_screen.dart:433,692`); common cash flow and Contribute still appear without common accounts (`493–520`), and transfer has no prerequisite CTA when fewer than two usable accounts exist. Account setup exposes raw enum names and lets ownership/currency change with no explanation of existing entries (`67–120`). **Fix:** show clear empty-group actions, disable unavailable transfer/contribution with a reason, and explain or prevent structural changes that would reinterpret existing records. Preserve `includeInNetWorth` and other existing account metadata during edits rather than reconstructing with defaults. **Accept:** zero, one, only-personal and only-common account scenarios explain what to do; editing an account does not silently alter unrelated settings or prior money meaning.

**UX-32 · P2 · Settlement history lacks a complete pending-state story.** Source-confirmed/design judgment: all contributing expenses precede history (`settle_up_screen.dart:707–810`); pending proposals have Confirm/Reject but no visible sent-on date, “Waiting for Anna” distinction, or clear withdrawal/rejection recovery (`832–946`). A proposal is still offered while all settled. **Fix:** put proposals requiring action immediately after the balance; label proposer/time/waiting party and local account effect; collapse the long explanation behind details; give reject/cancel a deliberate, recoverable interaction. When zero, lead with settled success and treat new record creation as secondary. **Accept:** users distinguish awaiting partner from needs-your-approval without opening a dialog; a long history never hides an outstanding proposal; rejecting cannot happen accidentally without feedback.

**UX-33 · P1 · Goals are create-and-add only, and “Contribute” implies money movement.** Source-confirmed: goal cards only expose contribution (`goals_screen.dart:611–623`), no edit/archive/delete/correction. Contribution directly increments goal totals without selecting an account or creating a transaction (`54–80`). **Fix:** add minimal goal management and a clearly labeled “Record savings” action if it is a progress tracker; explain that account balances are unchanged. Allow correcting mistaken contributions. Keep a true account-funded contribution as a separate later feature if necessary. **Accept:** users can rename/change target/deadline/archive a goal and reverse an incorrect addition; the UI never implies an actual bank/account transfer when it only changes progress.

**UX-34 · P1 · Emergency fund defaults present guesses as personal finance targets.** Source-confirmed/design judgment: when no sufficient data/goal exists, goals silently substitute HUF600,000/HUF450,000 (`goals_screen.dart:282–293`) and call the card auto-calculated (`502–506`). Both shared and personal funds appear regardless of selected scope, and the large gauge duplicates percentage information before actionable goals (`352–508`). **Fix:** use an insufficient-data explanation or explicitly editable suggested target; state the spending window and target-month assumption; keep scope consistent and condense duplicate summary visuals. **Accept:** a new empty database shows no apparently calculated target; users can explain how the target was derived and change its assumption; selected Personal/Shared scope is respected.

**UX-35 · P1 · Savings calculator accepts bad scenarios and compresses results.** Observed/source-confirmed: three unconstrained result columns overflow (`savings_screen.dart:364–390`), and invalid text silently becomes zero/default; years clamp but input remains unchanged (`84–90`). “Create Goal” immediately creates a new goal every tap (`395–419`) without reviewing its name or opening it. **Fix:** validate the scenario visibly, use responsive result rows, label projections as assumptions rather than guarantees, and confirm/save the scenario through a concise goal editor with a view-goal result. **Accept:** unreasonable/invalid values cannot create misleading goals; displayed assumptions equal calculation inputs; repeated taps do not accidentally create duplicate goals; results fit the audited matrix.

**UX-36 · P1 · Recurring billing presents a maintenance tool rather than a reliable schedule.** Observed/source-confirmed: header overflows; “Generate due now” iterates every rule, including future rules, without filtering due date (`recurring_screen.dart:393–399`), while generation doesn't advance the rule's next due date (`25–87`). Creation has no first-due/category/split choice and fixes category to the first (`103–109,274`); no edit/pause/delete action is exposed on cards (`429–470`). Success mentions `idempotent UUIDv5` (`404`). **Fix:** show due date and schedule, support edit/pause/remove, and make any Record due bills action process only eligible due items and advance next due consistently. Remove algorithm names from consumer copy; explain automatic behavior honestly if it is not scheduled. **Accept:** a future Netflix bill is not recorded by a due-now action; successful recording updates next due and gives a useful count; a user can correct/cancel a rule.

**UX-37 · P2 · Finding old transactions requires knowing a separate feature.** Source-confirmed/design judgment: primary Transactions has no search/date filter; History duplicates views/search/category/month controls (`history_screen.dart:87–200`) and cannot open a result (`225–246`). The month control has no direct date jump or clear current-month reset. **Fix:** make search/filter available from Transactions, share row/detail behavior, and give History a month picker, reset/clear filters and useful no-results actions. It can remain a separate monthly report if its purpose is explicit. **Accept:** a user can locate and open an old merchant transaction from the main Transactions area, clear filters, and return to the current month without dozens of chevron taps.

**UX-38 · P2 · Category management exposes implementation fields as the product.** Source-confirmed/design judgment: users see both language names in every row, a numerical sort-order avatar, raw hex labels, and a Sort Order input (`categories_screen.dart:63–75,106–123,205–214`). No archive/remove action is visible. **Fix:** show the current localized name by default, optionally reveal translation editing, use named color swatches with accessibility labels, and use simple reorder/archive controls. Explain Essential in terms of emergency-fund calculations. Preserve icon/parent metadata during edits. **Accept:** users can add/reorder/retire a category without understanding hex codes or numerical ranks; a translated name is optional; previous transactions remain intelligible after retirement.

**UX-39 · P1 · Export action labels describe files that are never produced.** Source-confirmed: Export CSV copies text to the clipboard (`export_screen.dart:252–264`); “Export Workbook (XLSX/TSV)” concatenates labeled CSV strings and copies them (`267–281`), not an XLSX workbook. JSON backup is also clipboard-only (`331–344`). The large table can be expensive and unwieldy. **Fix:** either create/share correctly typed files using already installed export/share packages, or name the exact present behavior “Copy CSV,” “Copy all sheets as text,” and “Copy JSON backup”; remove unsupported format claims. State exported scope/time range and give an explicit success outcome. Show a bounded preview/count. **Accept:** labels match a real file/share result or clearly state clipboard; an XLSX claim yields a valid workbook; cancellation/error does not report success; no unsupported assumption that clipboard equals safe durable backup.

**UX-40 · P1 · Restore fails outside the form and can mislabel errors as success.** Source-confirmed: the dialog is prefilled with the current JSON, restores directly on click, and closes on both success and parse failure (`export_screen.dart:368–407`). Error text is assigned to `_statusBanner`, whose card always uses a green check (`151–165`), and exposes raw exception text (`405`). **Fix:** keep invalid input and field-specific errors in the dialog; summarize what will be merged/replaced and ask for deliberate confirmation before applying; use success/error severity explicitly and preserve existing data on any failure. Prefer file selection when supported, with paste as an advanced route. **Accept:** malformed/unsupported JSON does not close the editor or mutate data; errors are not shown with a success icon; valid restore previews its effect and provides an understandable final result.

**UX-41 · P2 · Profile setup is too dense and photo selection is fragile.** Observed/source-confirmed: all profile, language, pledge, household, invite, test identity and cloud fields share one long screen. Avatar options wrap into vertical letters at HU320 (`auth_screen.dart:260–303`). Photo expects a remote URL (`305–315`), and `UserAvatar` does not provide image failure/loading handling (`theme.dart:1230–1237`). **Fix:** separate concise profile and household groups, place the avatar selector below the preview or use roomy choices, use accessible neutral avatar choices/initials and an optional photo picker, and always fall back gracefully for invalid/failed images. Localize palette names. **Accept:** editing a name/photo is easy to find; a long name, emoji, missing image, invalid URL or offline image produces a stable avatar; choices fit narrow/large-text layouts.

**UX-42 · P2 · Localization and product copy leak technical language.** Source-confirmed: account types use `.value.toUpperCase()` and compounding raw values (`accounts_screen.dart:96,153`); recurring frequency remains raw English (`recurring_screen.dart:446`); category labels expose hex/order; export sheet/month labels remain English (`export_screen.dart:226,241`); member badge says `members` regardless of language (`auth_screen.dart:408`); dates alternate ISO and dotted forms. Settings expose `Supabase`, APK/manifest/keystore/OTA details (`auth_screen.dart:493`, `settings_screen.dart:252–271`). **Fix:** centralize localized display names/date formatting, prefer user outcomes (“Cloud backup,” “App updates,” “Record due bills”), and move technical diagnostics behind a developer/about surface. **Accept:** a Hungarian walkthrough contains no raw enum/algorithm/format strings except intentional currency/file-format names; dates/counts are consistently localized.

**UX-43 · P1 · Recovery and empty/loading/error states lack a shared contract.** Source-confirmed/risk: many empty views only display a sentence (Transactions `177–184`, Goals `513–520`, Recurring `417–425`, Activity `67–77`); async export handlers have no consistent busy/error/mounted handling (`export_screen.dart:253–277,332–340`); offline/pending synchronization is not surfaced alongside recorded data. **Fix:** standardize a small set of states: purposeful empty with next action, filtered empty with clear/reset, in-progress action with duplicate-submit protection, local-only/pending sync, recoverable error with retry. Avoid dummy loading animations for synchronous data. **Accept:** every main screen has meaningful zero-data content; slow/failing clipboard/share/network actions preserve context and show truthful outcomes; pending writes are understandable without claiming they have synced.

## Consumer quality bar and verification requirements

These are practical design criteria, not claims that the app has been certified against a standard. Flutter's own release checklist calls for intelligible screen-reader controls, sufficient contrast, 48px targets, undo for important actions and usability at large scale factors. [Flutter accessibility](https://docs.flutter.dev/ui/accessibility). WCAG's contrast criterion specifies 4.5:1 for ordinary text and 3:1 for large text. [W3C contrast explanation](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

| Quality expected from a mature consumer app | Current position | Required evidence before closing |
| --- | --- | --- |
| A new user understands where to go and what the current number means. | Partial: many concepts explained, but unlabelled tabs and ambiguous periods. | First-use walkthrough of add expense, find old expense, inspect balance, record settlement; consistent period/currency language. |
| Data and system state are honest. | Blocked: invented series and simulated protection/connectivity. | No simulated success state presented as a real capability; charts reconcile with fixtures. |
| Every routine task survives a small phone and large text. | Failed: observed overflows and vertical letter wrapping. | Matrix above plus short landscape/keyboard-open scenarios; screenshots and zero-error assertions. |
| Important actions can be reversed or corrected. | Partial: storage soft-deletes exist, UI undo/corrections do not. | Delete/undo, draft discard, contribution correction, failed restore and cancellation tests. |
| Controls are operable by touch, keyboard and assistive technology. | Unverified/partial: semantics added to some controls, custom focus behavior absent. | Flutter semantics/tap/contrast checks and a physical-device TalkBack walkthrough. |
| The interface has one coherent visual language. | Partial: recognizable palette, competing card/action/semantic styles. | Side-by-side screen review in light/dark with normal/long data; functional color contrast measured. |
| The app handles absence, waiting and failure calmly. | Partial: some useful empty text, no consistent state system. | Empty DB, filtered empty, one account, unavailable capability, failed async action and pending sync cases. |

### Acceptance scenarios that should be retained as meaningful regression tests

1. All 16 routes at the four audited configurations render and scroll without framework exceptions; check both label wrapping and money legibility, not just error counts.
2. Transaction/transfer and account/budget/goal/recurring/category/settlement dialogs with 300px keyboard inset, EN/HU, 320px width and 200% text. Save/Cancel must remain reachable. Empty and dirty dismissal must differ appropriately.
3. Long input fixtures: 60-character names and categories; unbreakable merchant strings; note with newlines; emoji/non-Latin names; no avatar/failed image; many accounts/categories/goals; negative balances and multi-million amounts.
4. Empty database and prerequisites: no household, one/no profile, no accounts, one account, only common accounts, no transactions, no budgets, no matching filter results, insufficient emergency-fund history.
5. Truthful money fixtures: only current-month history, zero-income savings rate, future-dated entries, category budgets with rollover, EUR/RON/HUF transactions and goals, unchanged partner-paid shared edit, cross-currency transfer creation/editing.
6. Hide amounts across dashboard, activity, accounts, stats, goals, settlement, chart tooltips and semantics. Never rely only on checking trailing amount widgets.
7. Invalid entry never silently saves zero or an invalid exchange rate; errors remain next to the field; undo restores transaction accounting; failed restore preserves data.
8. TalkBack and keyboard can identify and activate every custom control exactly once; controls satisfy target-size/contrast checks; theme/language and supported privacy preferences survive expected lifecycle behavior.

## Recommended implementation order and scope boundaries

**First:** remove misleading success/history and close privacy/money-meaning gaps (UX-01–08). Where backend/native capability is unavailable, the UI fix is an honest disabled/local/demo state, not a new authentication/sync/biometric architecture.

**Then:** fix the shell/shared components, measured contrast and responsive primitives (UX-09–19), and use them while correcting core entry/edit/transfer/settlement behavior (UX-20–27). This prevents each supporting screen from inventing another layout workaround.

**Then:** close the dashboard and screen-specific lifecycle/information hierarchy gaps (UX-28–43). Recheck the matrix and focused regression scenarios after the final integrated styles are present, followed by real Android keyboard, touch and TalkBack verification.

The source stores domain data in memory (`app_database.dart:14–32,616–618`), and the available UI does not demonstrate a complete durable authenticated financial product. This is a production blocker beyond a visual redesign. The UI audit must not imply that making screens polished solves persistence, remote authorization, reliable synchronization, release updates or biometric enforcement. Preserve existing domain semantics and user changes; close UI behavior with the smallest coherent implementation and report any remaining capability gaps explicitly.
