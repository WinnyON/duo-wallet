# UI/UX implementation plan

Based on the 4 November 2026 [audit](ui-ux-audit.md), including its rendered evidence. This plan covers all 43 findings. Preserve the current redesign and unrelated working-tree edits. Implement corrections in place; do not replace the application or add a design framework.

## Scope and readiness

Deliver truthful, accessible local/demo UI now: actual transaction-derived charts, correct periods/currencies, complete privacy masking, responsive layouts, usable navigation/forms, reversible edits, and honest capability/export states. Retain coral/teal brand accents with accessible functional variants.

UI completion **does not establish production readiness**. Durable storage, actual authentication/household authorization, reliable remote synchronization, enforced app lock, verified update delivery, and real bank payments are separate implementation/release work. Installed packages and configured environment flags do not prove those capabilities work. Disable unavailable controls and consistently explain local/demo mode. Do not invent sync, authentication, security, or financial-success states to satisfy screenshots.

## Shared helper contract

Keep existing `Pressable`, `DuoAmount`, `DuoCard`, `DuoSectionHeader`, `DuoCircleButton`, `UserAvatar`, and theme/color extension signatures compatible. Improve their implementations rather than creating replacement component families.

The following small additive helpers are owned by A in `theme.dart`; use them across editors and activity surfaces:

```dart
double? parsePositiveAmount(String text, {bool allowZero = false});
Future<bool> confirmDiscardChanges(BuildContext context, {required bool dirty});
String activityDisplaySummary(
  ActivityEvent event, {
  required String locale,
  required bool hideAmounts,
});
```

`parsePositiveAmount` accepts a trimmed plain decimal with either period or comma as decimal separator, rejects mixed separators, malformed/nonfinite/negative input and values beyond safe supported money precision; it never silently substitutes zero. Zero is accepted only when requested. Signed balances and scenario returns need explicit signed validation instead of abusing this positive helper. Inline field validators still supply localized errors and range rules. FX rates require strictly positive finite values.

`confirmDiscardChanges` returns true immediately for a pristine draft; dirty drafts get localized Keep editing / Discard actions, and only explicit Discard returns true. Owners must guard Back and explicit Close, and prevent uncontrolled barrier/swipe dismissal where it bypasses this check. A non-dismissible barrier/drag with an accessible close affordance is acceptable; blank forms still close in one action. Do not introduce a generic form framework.

`activityDisplaySummary` returns the existing localized summary normally. Under masking, return amount-free event-type copy (transaction recorded, savings updated, settlement recorded, etc.) using structured type/metadata where available. Unknown event types use a generic amount-free activity label. Never regex-rewrite arbitrary digits in merchant names. Root and C use the same helper. Mask amounts in semantics and chart labels/tooltips as well. Explicitly opened editors may reveal values; the privacy control explains that boundary.

A also owns a consistent `AppShell.openDrawer(context)` access path in `router.dart`; keep this existing API stable and make it work from nested scaffolds. Top-level screen app bars call it; details get Back with a safe fallback route.

Root adds `String Money.formatNumber({String locale = 'hu', bool compact = false})`, preserving locale decimal/group punctuation. `Money.format` composes this number with the existing currency placement policy; `formatCompact` delegates. A uses `formatNumber` inside `DuoAmount`, eliminating its independent punctuation/compact formatter. No comma replacement anywhere. Full exact values remain available to semantics/detail views when a compact visual is used; hidden amounts never expose them.

C's budget helper returns the category/scope-filtered spent amount and rollover-adjusted effective limit for an explicit month and user, reusing existing Budgets semantics. Publish its exact Dart signature to root when extracted; Dashboard and Budgets must call the same function. No second approximate implementation.

B exposes `Future<void> showTransactionDetails(BuildContext context, Txn transaction)` from the transactions presentation file, with clear Edit/Delete actions; root calls it from History and B uses it from Accounts and Transactions. Transfer edit routes to `TransferSheet`, preserving the original transaction. Keep `QuickAddTransactionSheet.show` compatible for existing entry points.

## Implementation details that protect financial data

- Account, category, recurring and goal models lack universal copy helpers. Reconstruct existing models only while explicitly carrying every unchanged field; ask root for minimal model support when null/deletion state cannot be represented safely.
- `restoreFromJson` currently mutates maps while parsing and restores only part of exported data. Fix transactionality at the storage boundary, not with a UI try/catch alone. Validate shape/types, supported schema and identities before commit. Preserve existing household/privacy boundaries; backup import must not expose inaccessible personal records. Document merge-by-ID behavior and unchanged versus replaced records in the preview.
- Root may add an optional `meId` argument to `exportVisibleJson` while preserving existing no-argument callers; all UI export/backup paths pass the current identity so demo partner-private records are excluded. The JSON artifact must match its stated visible-data scope.
- Category retirement must retain labels on historical transactions. If soft deletion hides the category from lookup, archive/hide from new-entry pickers while resolving old IDs, or make a minimal explicit model/storage change. Do not delete transaction references.
- Calendar recurrence advances by frequency (daily/weekly/monthly/yearly as supported), not a fixed 30-day duration. Preserve the intended day where possible and clamp month-end safely. Respect end date/paused state; no backend scheduling claim.
- Monthly currency aggregation uses trustworthy stored base amounts or grouped native values. Do not fetch a current rate and present it as an historical exact conversion. Explain any estimate and rate date if conversion is unavoidable.
- Undo and restore must preserve existing privacy rules: changing scope still follows storage's tombstone/new-ID behavior; restoring an item cannot revive another user's private transaction into a shared view.

## Verification and closure

Root owns shared tests to avoid collisions. Workers supply a concise list of changed behavior and edge cases to root; run only focused analysis while other owners are editing. Root runs final `flutter analyze` and the full test suite after integration.

1. Convert the temporary collecting probe into a portable failure-asserting regression test: do not swallow Flutter errors. Use SDK-relative bundled fonts or portable test font setup, not a machine-specific font path. Cover the 16 routes at EN360×800/1×, HU320×640/1×, HU320×640/1.5×, EN360×800/2×, plus 320×568 and dark-mode key surfaces. Scroll long pages and exercise dialogs. Screenshot evidence complements, never substitutes for assertions.
2. Exercise transaction/transfer and account/budget/goal/recurring/category/settlement editors with a 300px keyboard inset at 320px/200% EN/HU. Assert reachable Save/Cancel, valid grouped amounts, no framework error, and preserved dirty input on rejected dismissal.
3. Test money locale matrix, one-month/no-history chart data, future transactions excluded from month, cross-currency transfer create/edit, partner-paid unchanged edit, budget category/rollover parity, native-currency goal totals, and month-opening flow reconciliation.
4. Test direct private-account routes and retained-page identity switches. Test full privacy strings/semantics, including activity prose and chart labels; do not only inspect DuoAmount text.
5. Test invalid/empty/NaN/infinite/decimal-comma entry, signed balances, Undo's accounting effect, due-only recurring plus month-end advancement, goal correction and duplicate-save protection, invalid later-row restore atomicity and valid merge preview/outcome.
6. Test empty/one-account/only-common/missing-household datasets, long names/merchant/notes, emoji, failed avatar, extreme/negative amounts, no matching filters and insufficient emergency history. Verify meaningful next actions.
7. Run Flutter semantics and Android tap-target checks, keyboard single activation/focus checks, reduced-motion behavior, and measured contrast for functional tokens in both themes. Root records remaining physical Android/TalkBack/software-keyboard/share-picker/native-back checks as unverified until actually performed.

The final delivery should link the updated implementation and evidence, summarize automated verification, and list genuine remaining production blockers. No audit ID is closed solely because its requested backend capability is disabled; record “UI corrected; capability unavailable” where applicable. No live auth, durable persistence, cloud sync, lock enforcement, update delivery, or physical-device verification is implied by this plan.
